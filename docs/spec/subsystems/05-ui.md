# 05: User interface (windows, modes, layouts, browser, preferences, localisation, theming, rendering)

Status: first draft from static evidence (symbols, strings, bundled resources) plus the public rekordbox 7.2.18 English instruction manual. No decompilation yet. Items marked **(inferred)** are reasoned from names or context rather than observed behaviour.

Evidence conventions: `Class::member` is a demangled symbol or a `classes.tsv` row; `"Text"` is a string from `strings.txt` or a key in the `.lang` files; `skins/...` is a bundled resource path relative to `Contents/Resources`; "Manual p.N" is the public instruction manual page. All evidence lives outside the repo under `/opt/rekordbox/7.2.19/analysis` and the unpacked app bundle.

Clean-room reminder: this spec names rekordbox labels and identifiers only so we can check feature parity. Cuepoint ships its own wording, iconography, colours and layout proportions. No skin artwork, icons, translations, tutorial images or product names are copied.

---

## 1. Purpose

The UI subsystem is everything the DJ sees and touches on screen:

- The application shell: single main window, native menu bar, mode switching, full screen, secondary windows (video output, preferences, pad editor, MIDI setting, info/notifications).
- Four application modes (EXPORT, PERFORMANCE, LIGHTING, EDIT) and a family of deck layouts per mode.
- Deck, mixer, effect, sampler, sequencer, GROOVE CIRCUIT, MIX POINT LINK, microphone, recording, video and lighting panels.
- The scrolling and overview waveform renderers, which are the most performance-critical drawing in the app.
- The library browser (tree, track list, filters, palettes, related tracks, track suggestion, streaming "wiki" pages, sub browser, split screen).
- Preferences (11 categories, roughly 60 tabs, several hundred persisted keys), keyboard mapping editor, MIDI learn table.
- Dialogs, wizards, first-run introduction, tutorial, questionnaire, notifications, tooltips.
- Localisation (18 UI languages), font selection, dark and light colour themes, high-DPI.

Out of scope here (owned by other subsystem specs, referenced only): audio engine and DSP behind the controls, library database, analysis algorithms, PRO DJ LINK protocol, controller HID/MIDI mapping semantics, lighting DMX output, video decoding, cloud and streaming services. This spec defines the panels that expose those features and the settings that configure them.

## 2. Screen and panel inventory

### 2.1 Application shell

**Application object.** Starts the app, enforces a single instance (a second launch is forwarded to the running one), shows a splash, initialises crash reporting and analytics, and owns the command manager used by menus and keyboard shortcuts. ### 2.3 Deck layouts

**EXPORT mode layouts** (Manual p.62 to 66, View menu):
1. 1 PLAYER: one large deck with operation panel, track info, enlarged waveform, function panel (CUE/LOOP or GRID), sub-info panel (MEMORY, HOT CUE, INFO tabs).
2. 2 PLAYER: players A and B with a crossfader between them, compact function panels with tempo, pitch bend, master tempo.
3. DUAL PLAYER: as 2 PLAYER plus per-player auto gain, 3-band EQ kill, key shift, key sync and DUAL CONTROL (play/pause both).
4. SIMPLE PLAYER: play/pause and volume only.
5. FULL BROWSER: no player panel.

3. 4 Deck Horizontal.

Modifiers: Show/Hide Pad and Platter per deck pair (horizontal only), Split Screen (second browser), enlarged-waveform ordering for 4 decks, pad display mode, FX panel layout, and stems control layout.

**Legacy skin layout format (EXPORT players).** Five XML files describe absolute-positioned widgets for the export-mode players. Structure in our own words: a root `skin` element with a `Window` block (window size and client background size), then sections `Master`, `Player`, `Mixer`, `Browser`/`Browse`, `ProDJLink`. Each widget element (level meter, LED, slider, button, realtime text, link-status widgets) carries a name, position, optional size, image paths for on/off/over/pressed/disabled states, font name/size/style/colour, tooltip key and four anchoring flags (`Horizonal`, `Vertical`, `Extension`, `Move`) that say how the widget reflows when the window grows. Cuepoint does not need this format; it documents that EXPORT players are fixed-geometry layouts with stretch anchors (inferred). `djplay::Skin::{createObject, changeSkinPos}`, `djplay::SkinFunctor::{getBoolean, getColour, getInteger, getPos, getSize}`, `djplay::Widget*Parameter` classes, `djplay::UiManager::{initSkin, resizeSkin, resizeSkinProDJLink}`.

## 4. Localisation and theming

### 4.1 .lang format (observed)

Location `Contents/Resources/locale/*.lang`, UTF-8, CRLF line endings. The format is JUCE's `LocalisedStrings` text format, wrapped in `@code` / `@endcode` lines (a documentation artefact that the loader tolerates, inferred):

- Header: a comment banner, then `language: <Name>` and `countries: <codes>` lines (indented).
- Comments start with `#`. Group markers are comments of the form `# group: <Name>`; they are informational only.
- Entries: `"<english source>" = "<translation>"`, one per line. The key is the literal English UI string, so English needs no table: the English file only carries a handful of identity entries (language names, `+/-6` style tokens).
- Escapes inside quotes: `\n` newlines (734 entries in German use them) and `\"` quotes.
- Empty translations (`= ""`) are present and mean "fall back to the English key" (inferred from JUCE behaviour).
- No printf placeholders are used (one stray `%20p` URL fragment). Runtime substitution uses literal tokens replaced in code: `xxxxx` (98 uses), `xxxx`, `yyyy`, `XXXXX`. Square-bracket text such as `[Preferences]` is literal UI cross-reference, not a placeholder.

## 5. Rendering as observed

### 5.1 Pipeline
- Most UI is JUCE software (CoreGraphics) painting of components with look-and-feels and SVG drawables (`SvgHelpers`, `SVGImageHelpers`, `browse::DrawableCache`, `ImageHelper`).
- Performance-critical views (waveforms, video, lighting editor waveform) are rendered on the GPU with a dual backend:
  - **Metal (primary on macOS).** `MetalLayer` attaches a `CAMetalLayer` to a component, registers renderers with z-order and frame rectangles (`MetalRenderer::{setMetalFrame, setMetalZorder}`), and is driven by `MetalDisplayLink` (a CVDisplayLink-backed callback with `setFrameRate`). `MetalContext` offers immediate-mode primitives: fill rect, polygon, triangle, lines with vertices, textures, transform, scale (`getCurrentScale`). `MetalPrimitive` holds wave vertex and index buffers. `MetalCachedComponentImage` lets ordinary JUCE components be cached into Metal textures. Shaders in `default.metallib` (36 KB): `vertexShader`/`fragmentShader` (flat colour), `vertexShaderDistance`/`fragmentShaderDistance` (inferred: distance-based anti-aliased lines or rounded shapes), `vertexShaderWave`/`fragmentShaderWave` (waveform), `vertexTextureShader`/`fragmentTextureShader` (images, markers, text bitmaps), `computeUpdateShader`/`computeUpdateImageShader` (compute updates of wave buffers or images, inferred).
  - **OpenGL (fallback and video).** `rb::OpenGLContext`, `rb::OpenGLRendering` (a forked JUCE GL renderer with shader programs, cached images, frame buffers), `djplay::OpenGLManager` (lines, dashed lines, rects, triangles, textured quads), `djplay::OpenGLRenderComponent`, NSOpenGL classes, CVOpenGLTextureCache for video frames. `MainComponent::isOpenGLDisabled`, `MetalHelpers::{isMetalEnabled, isMetalDisabled}`, `MetalRenderComponentImpl::MetalEnableFirst` decide the backend.
- Render suspension during layout changes and modal states: `MetalLayer::{renderPause, renderRestart, renderStop}`, `MainComponentListener::{componentRenderSuspend, componentRenderResume}`, strings `"DisableAdaptiveVsync"`, `"RenderDelay"`, `"MainPanel::setMainComponentHeight (renderRestartRequest)"`.
- A high-resolution UI timer (`djplay::UiTimer::hiResTimerCallback`) drives deck state polling; blinking indicators share one `djplay::BlinkManager`.

### 5.2 Waveform drawing
- Waveform data comes from analysis files at several resolutions (`djplay::WaveDataZoom::getResolution`, `djplay::WaveZoom`, `djplay::WaveData`, `djplay::WaveDataCDJ`), converted into vertex and index lists (`djplay::WaveView::{createVertexList, createIndexList, create3BandsVertexList, create3BandsWaveInfo}`) uploaded once per track and zoom tier, then scrolled with a transform each frame (inferred from `setUiWaveScroll`, `drawWaveInfoIndexMetal`, `MetalVertexWaveImage::loadVerticesMetal`). A texture path also exists (`createWaveTexture`, `MetalWaveImage`). Deletion is deferred to a background "wave deleter".
- Markers and labels are pre-rendered to textures (`createHotcueImage`, `createSongStructImage`, `createSilentTextImage`, `createCaptureAreaImage`, `SmartCueImageGenerator::generateRecoloredImageListFromSvg`).
- Drawing rate preference: High, Medium, Low speed. The numeric frame rates are not in strings and need Ghidra (see 7). "Low" disables video, implying video shares the display link.
- `"thumbnailAnimationFps"` controls lighting thumbnails.

### 5.3 High-DPI
- Retina awareness through `NSWindowListener.retina_`, `backingScaleFactor`, `setContentsScale:` on the Metal layer, `MetalContext::getCurrentScale`. JUCE handles component scaling; bitmap assets exist in single resolution (PNG) with SVG for most newer icons.

### 5.4 Video rendering
- GL shader programs for the video mixer and 32 transition effects: additive, cube, cut, difference, displace, doors, drop, fade, flip, glow cross, grid, grid2, hold, iris, luma key black, luma key white, pixelate, rec expansion, RGB, rolling blinds, sine wave, slide horizontal, spin horizontal, spin vertical, squeeze horizontal, squeeze vertical, strobe, swap, switch, warp, wipe horizontal, wipe vertical; plus a generic VFX shader. `FragmentShader::fshader_tfx_*`, `VideoPanelSS::renderTFX`, `VideoPanel::changeFrameRate`.
- Syphon server publishes the output texture (macOS only).

### 5.5 egui/eframe/wgpu fit (research summary)
- eframe on wgpu gives Metal on macOS, Vulkan/DX12 elsewhere. egui repaints on demand; for decks we call `request_repaint()` every frame while any deck plays, and rely on the surface present mode (FIFO for vsync, Mailbox where available) to pace at display refresh (60 to 120 Hz on ProMotion).
- Custom GPU drawing inside egui: `egui_wgpu::Callback` with a `CallbackTrait` implementation (prepare + paint) lets us record our own render pass commands into egui's pass, with our own pipelines, vertex buffers and uniforms, clipped to the widget rect. This matches rekordbox's "upload once, scroll by transform" approach.
- Multiple native windows (video output, preferences, pad editor) via egui viewports (`ViewportBuilder`, immediate or deferred viewports).
- Accessibility via AccessKit, built into egui.
- Text: egui's built-in text layout does not do complex shaping; acceptable for our 18 UI languages if we bundle fallback fonts with CJK coverage. For track metadata in complex scripts, a shaping path (for example a HarfBuzz port such as harfrust/rustybuzz feeding custom glyph runs, or a parley/cosmic-text based layout) is a later enhancement.

## 8. Rust plan

### 8.1 Crates and modules

- `cuepoint-ui` (existing): all egui widgets and panels. Proposed modules:
  - `app/`: shell, command registry, menu model, mode state machine, window/viewport management, persisted window state.
  - `modes/`: `export`, `performance`, `lighting`, `edit` screen compositions.
  - `layout/`: deck layout presets (data-driven), split screen, panel visibility, responsive rules.
  - `deck/`: track info, virtual jog, tempo, pads (one module per pad mode), grid/phrase edit, stems controls.
  - `waveform/`: renderer (see 8.3), overview, preview, CDJ preview, overlays, interaction.
  - `browser/`: tree, track list (virtualised table), filters, palettes, side panels, streaming pages, intelligent playlist editor.
  - `panels/`: mixer, fx, sampler, sequencer, groove_circuit, mix_point_link, mic, rec, automix, link_status, lighting_mini.
  - `prefs/`: preference schema and pages, search index.
  - `dialogs/`: alerts with don't-ask-again, progress, managers, wizards.
  - `theme/`: tokens, dark and light palettes, waveform and cue palettes, icon atlas.
  - `i18n/`: string catalogue access and locale switching.
- `cuepoint-render` (new, proposed): wgpu pipelines for waveform, markers, lighting timeline; no egui dependency so it can be benchmarked and tested headless. `unsafe_code = "deny"` holds (wgpu is safe).
- `cuepoint-video` (existing): video decks, transitions, CD+G decoder (pure Rust), output window integration; Syphon/Spout in a separate `cuepoint-platform-share` crate that is allowed `unsafe` for Objective-C/COM interop.
- `cuepoint-core` (existing): settings store types shared with other crates.

### 8.2 State and architecture
- Unidirectional flow: UI reads immutable snapshots of engine state (published each audio block via a lock-free triple buffer) and sends commands over a channel. No UI code touches the audio thread.
- One `Command` enum with stable string IDs used by menus, keyboard mappings, MIDI learn and controller mappings. Keyboard mapping files are our own TOML or JSON with the same category grouping as 3.9.
- Settings: a typed schema (`struct Settings` with serde) where every field carries metadata: page, tab, label key, default, range, mode visibility, restart-required flag, and search keywords. Pages render from metadata where possible so search and "restore defaults" come for free. Stored as versioned TOML in the platform config directory; side files only where data is large (column layouts, FX presets).

### 8.3 Waveform renderer
- Data: per track, precompute GPU-ready column buffers at 3 to 4 resolution tiers (for example 150 columns per second, plus 1/4 and 1/16 decimations) from the analysis crate's waveform output; for RGB and 3Band store per-column low/mid/high amplitudes; for BLUE store amplitude and brightness.
- Upload once per track to a storage buffer; draw with one instanced quad per visible column (or a triangle strip), with a uniform for scroll offset in samples, zoom, orientation (horizontal/vertical) and colour mode; the vertex shader positions columns, the fragment shader colours. Scrolling is a uniform change, so per-frame CPU cost is constant.
- Overlays (grid lines, cues, loops, phrases, vocal strip, slicer, censor, automix fades, capture areas) are batched as instanced rects and lines plus a glyph/marker texture atlas generated from our own SVGs with resvg at the current scale factor.
- Integrate through `egui_wgpu::Callback`; each deck view issues one callback. Target: 4 decks plus overviews at 120 Hz on Apple silicon with under 1 ms GPU time per frame; drawing-rate setting maps to frame pacing (every frame, every second frame, every fourth frame) once the observed rates are known.
- Interpolate playhead position from the engine's sample clock and the frame's presentation time to avoid judder (engine publishes position plus timestamp).

### 8.4 Layout system
- egui panels (`TopBottomPanel`, `SidePanel`, `CentralPanel`) for the fixed shell; a small data-driven layout description per preset (rows of regions with min/max sizes and visibility predicates) for deck areas, so the 2/4 deck, horizontal/vertical and browse presets are data, not code. Optional dockable layout via egui_dock as a post-parity extra.
- Minimum window sizes per preset; breakpoints hide secondary controls first (as rekordbox hides pads/platter).

### 8.5 Localisation
- Our own string catalogue in Fluent (`.ftl`), keyed by stable message IDs, one file per locale, en-AU and en-US first, then the same 17 additional languages as rekordbox. We do not import or ship rekordbox translations.
- Compile-time check (build script or test) that every ID used in code exists in the base locale and that placeholders match; runtime fallback chain locale, then base English.
- Language switching at runtime without restart (egui re-lays out every frame).
- Fonts: bundle Inter (Latin, Greek, Cyrillic) and Noto Sans CJK subsets (SC, TC, JP, KR) as fallbacks; load lazily by locale to limit memory.
- A `.lang` reader is not needed; if community translators want a simpler format we can add an importer for a plain `"key" = "value"` file later.

### 8.6 Theming
- Design tokens (surface, raised, text primary/secondary, accent, deck colours 1 to 4, meter ranges, warning, waveform palettes, cue palettes) defined once; Dark and Light themes as token sets; egui `Visuals` derived from tokens; custom widgets read tokens only. Optional "follow system appearance".
- Our own icon set in SVG, rasterised per scale factor into a texture atlas.

### 8.7 Accessibility
- AccessKit through egui: every control gets a role, label (from the i18n catalogue) and value; decks expose play state, BPM and key as live regions.
- Full keyboard navigation of browser and preferences; visible focus rings; tooltips reachable by keyboard.
- Colour-blind-safe waveform and cue palettes as additional options; respect reduced motion for animated thumbnails.
- Minimum text size and contrast checks in theme tests.

### 8.8 Parity test strategy
1. **Inventory tests.** A machine-readable checklist (YAML in `docs/spec/`) generated from sections 2 and 3; a test asserts every listed panel ID and preference key has a registered implementation (panel registry and settings schema introspection).
2. **Snapshot tests per panel.** egui_kittest renders each panel headless with fixture state (empty, loaded track, playing, looping, cue-dense track) in Dark and Light, at 1x and 2x, in en and ja; images compared with a perceptual threshold. These protect our own design, not a pixel match with rekordbox.
3. **Behavioural comparison with rekordbox.** For each panel, a scripted interaction (for example "load fixture track to deck 1, set hot cue A at 0:32, enable loop 4 beats") is run in Cuepoint through the command API and manually or with macOS UI automation in rekordbox; we compare state observables (cue positions, BPM, key text, list order, filter results), not pixels. Screenshots of rekordbox stay outside the repo and are used only by a reviewer for layout parity (region presence and order), recorded as pass/fail in the checklist.
4. **Waveform numeric tests.** Given an analysis fixture, assert column heights and colour classes produced by our renderer's CPU reference path match the decoded analysis data (cross-checked with question 2), and that GPU output matches the CPU reference within tolerance (render to texture, read back).
5. **Performance tests.** Headless wgpu benchmark of 4 decks plus overviews per frame; CI budget alarms on GPU time and CPU time per frame.
6. **Localisation tests.** Missing-ID and placeholder checks for all locales; pseudo-locale (expanded, accented) snapshot pass to catch truncation.
7. **Accessibility tests.** AccessKit tree snapshot per panel: roles and names present, focus order stable.
8. **Interaction scripts.** egui_kittest drives clicks, drags, scroll and key presses for: layout switching, split screen, column reorder and resize, filter combinations, preferences search, keyboard remapping, dialog "don't ask again" persistence.

### 8.9 Build order (suggested)
1. Shell, command registry, settings schema, theme tokens, i18n scaffolding.
2. Browser (tree, track list, filters, search) against the library crate.
3. Single deck plus waveform renderer; then 2 and 4 deck layouts.
4. Mixer, FX, sampler panels; preferences pages as their engines land.
5. EXPORT mode layouts and link status panel.
6. EDIT mode, LIGHTING mode, video panel, remaining dialogs.
